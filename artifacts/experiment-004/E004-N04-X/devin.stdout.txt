## Summary

**Reproduced:** `test_self_removal_does_not_skip_the_next_subscriber` failed with `['first']` — the second subscriber never saw the event.

**Root cause:** `SubscriptionList.__iter__` returned `iter(self._items)`, a live iterator over the backing list. During `EventHub.publish`, when `remove_self` called `hub.unsubscribe(first)`, `SubscriptionList.remove` ran `self._items.remove(subscription)` mid-iteration. The second subscription shifted from index 1 → 0 while the iterator advanced to index 1 (now out of bounds), so iteration ended early and `second` was skipped.

**Fix** (one line, [subscriptions.py:28-29](file:///workspace/src/signalhub/subscriptions.py)): `__iter__` now returns `iter(tuple(self._items))` — a snapshot of membership taken when iteration begins. This matches `docs/delivery.md`'s "callbacks belong to the current delivery cycle": the delivery set is fixed per `publish` call, and fixing it at `__iter__` (the ownership boundary) protects every consumer, not just `publish`.

**Verified semantics:**
- Self-removal mid-delivery → next subscriber still fires (the bug)
- Unsubscribing a *later* subscriber mid-delivery → it's in the snapshot but `active=False`, so the existing check in `publish` skips it correctly
- Subscribing mid-delivery → new callback joins the *next* cycle, not the in-flight one
- Nested `publish` → gets its own snapshot, delivered synchronously; an outer-cycle removal doesn't corrupt it
- `once` subscriptions still run exactly once
