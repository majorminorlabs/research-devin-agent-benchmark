## Diagnosis

`test_redirect_302_relative` failed because a `Location: ///i8n.example2.com/302` header produced `http://www.example.com/i8n.example2.com/302` instead of `http://i8n.example2.com/302` — matching upstream scrapy issue #4032.

Chain of the bug in [redirect.py](file:///workspace/scrapy/downloadermiddlewares/redirect.py):

1. `response.headers['location']` returns bytes (`Headers.__getitem__` normalizes values to bytes), e.g. `b'///i8n.example2.com/302'`.
2. `safe_url_string` runs it through `urlsplit`, which treats only `//` (exactly two slashes) as a netloc marker — `///x` parses as `netloc=''`, `path='/x'`. So `location` becomes `/i8n.example2.com/302`.
3. `urljoin(request.url, location)` then resolves it as a root-relative path on the *original* host → wrong URL.

## Fix (matches upstream PR #4042)

In `RedirectMiddleware.process_response`, protocol-relative locations (`//…`, including `///…`) are now rebuilt with the request's scheme before joining:

```python
location = safe_url_string(response.headers['Location'])

if response.headers['Location'].startswith(b'//'):
    request_scheme = urlparse(request.url).scheme
    location = request_scheme + '://' + location.lstrip('/')

redirected_url = urljoin(request.url, location)
```

(`urlparse` added to the `six.moves.urllib.parse` import; header lookup switched to canonical `Location`.)
